# ADR-0002 活动/历史双表 + 单事务原子移动

- 状态：接受
- 日期：2026-11-23
- 影响：DDL（`02b-contract.md §2.1 §2.2`）、`lld/02 §3.2`

## 背景

需要「活动告警」与「历史告警」两套视图，并且「清除」要一条事务把记录从活动挪到历史，重复点击不能产生两条。候选：

1. 单表 + `status` 列（`ACTIVE/CLEARED`）+ `cleared_at`；
2. 双表 + 移动。

## 决策

**双表** `alerts_active` / `alerts_history`；清除用一个事务内「先 insert history，再 delete active」。

- 活动表 `fingerprint` 唯一索引 → 去重天然只在活动范围内生效。
- 历史表主键 = 同 id → 重复清除必然冲突，幂等由数据库保证。

## 理由

1. 去重需要「活动内唯一」，而历史可以存在同 fingerprint 的多条。单表加 `status` 就必须用**部分唯一索引**（`where status='ACTIVE'`），也能做到，但每次查询都要带 `status` 谓词，漏写就串数据。
2. 双表让「活动列表」查询天然只剩未清除数据，索引更小、更快。
3. 「移动」语义在审计与演示上都更清楚：历史不可变。

## 后果

- 正：列表查询简单；幂等靠主键；`alert_event` 不需要随移动改归属。
- 负：清除要两条语句（必须同事务）；`alert_event` 不能加 FK（会跨表移动）；详情接口要查两张表。
- 迁移成本：二期若要「确认(ACK)」中间态，需在活动表加状态列而非第三张表。

## 替代方案

- 单表 + 部分唯一索引：可接受，但查询处处要过滤状态，错误率高。
- 双表 + 软删除：会同时存在两份数据，违背 I-H1。
