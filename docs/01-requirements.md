# TriageDeck 需求文档 v1

> 定位：复刻版作品的**唯一需求源头**。后续设计、POC、代码、测试都必须能追溯到这里的编号。
> 写法：尽量像"用户/业务方提要求"的口吻，技术上怎么实现不在这里定。

---

## 0. 背景与角色

**一句话背景**：值班人员现在要在两个地方看告警、要单独去后台看谁登录过系统，处理完一条告警之后也没有记录可查。我们希望有一个地方，既能处理告警，又能回看"谁在什么时候做了什么"。

**角色**

| 角色 | 是谁 | 关心什么 |
|---|---|---|
| 值班工程师（Operator） | 一线值班的人 | 现在有什么告警、严重不严重、处理完要能清掉 |
| 运维主管（Admin） | 带班/负责的人 | 处理得及不及时、谁处理的、有没有人越权 |
| 只读观察者（Viewer） | 协作方、新人、领导 | 只看，不动手 |
| 外部系统（System） | 设备、其他服务 | 能把告警报进来 |

**术语**（后面统一用这几个词，避免混）

- **活动告警**：还没被处理掉的告警
- **历史告警**：已经被清除的告警
- **清除**：把人处理完的告警从活动列表移到历史
- **同一条告警**：来源、类型、资源、事件编号四项都相同的告警
- **审计记录**：一条"谁、什么时候、对什么、做了什么、结果如何"的记录

## 1. 认证与权限

### US-A1 用企业账号登录，不要另建一套账号

作为一个用户，我希望直接用工号/企业账号登录，不想再记一套新密码。

**验收标准**
- 打开系统首页时，如果没登录，会跳到统一的登录页（Keycloak）
- 登录成功后回到原来想去的页面，不用手动再点一次
- 系统内任何地方都不需要用户输入密码，密码只在登录页输入
- 刷新页面后不需要重新输入密码（企业会话还在，就静默续期）
- 登录态不写进浏览器本地存储，只存在内存里（关掉浏览器即失效）

### US-A2 能正常登出

作为一个用户，我希望点"退出"之后真的退出，而不是只把页面清空。

**验收标准**
- 点退出后回到登录页
- 退出后再访问任何需要登录的页面，会重新要求登录
- 这次退出会在审计里留下一条记录（见 US-C1）

### US-A3 不同角色看到的和能做的不同

作为一个只读观察者，我希望我能看告警，但不能误操作。

**验收标准**
- 三种角色（值班工程师 / 运维主管 / 只读观察者）登录后，界面基本一致，但"清除"这类操作按钮对只读角色不可用（禁用或隐藏）
- 只读角色能看活动告警、历史告警、审计记录
- 值班工程师能清除告警，能看审计
- 运维主管具备值班工程师的全部能力

### US-A4 绕过界面直接调接口也不行

作为系统的负责人，我希望权限真正的判断在后端，而不是靠前端不显示按钮。

**验收标准**
- 用无权账号直接构造请求（绕过页面）去清除告警，必须被拒绝
- 拒绝时返回明确的错误（403），而不是静默失败
- 这次被拒绝的尝试必须被记录下来（见 US-C3）

### US-A5 调整"谁能干什么"不用改代码

作为一个负责人，我希望以后要改权限（比如临时让观察者也能清除），不用改代码、不用重新发版，改配置就行。

**验收标准**
- 权限规则集中在一处可读的配置里，能看懂"哪个角色能对哪类资源做什么动作"
- 改一条规则后（重启或热加载），同一个账号的行为随之变化
- 这个变化能被现场演示：改之前 403，改之后 200

## 2. 告警

### US-B1 外部系统能把告警报进来

作为设备/其他服务，我需要一个稳定的方式把故障报给平台，并且两种方式都行。

**验收标准**
- 支持 HTTP 上报，字段至少包含：来源（哪个系统）、类型（什么故障）、资源（哪台机器/哪个实例）、事件编号（设备侧的规则号，可选）、严重级别、描述、发生时间
- 支持 Kafka 投递，同一套字段
- 上报成功返回一个回执编号（告警 id），方便排查
- 必填字段缺失时返回明确的校验错误（400），不能默默吞掉
- 通过 Kafka 投进来的告警，3 秒内出现在活动列表

### US-B2 同一个故障反复报，不要刷屏

作为值班工程师，我最怕的是同一台机器连发 50 条一样的告警，把真正的新问题埋掉。

**验收标准**
- 来源、类型、资源、事件编号四项相同的告警，在 10 分钟内重复上报时，**始终只有一条**
- 重复上报时，这条告警的"发生次数"累加、"最近发生时间"更新，其余不变
- 严重级别从低变高（比如警告变严重）时，更新严重级别，但**仍然是同一条**，不新建
- 资源不同、或类型不同，就不能合并
- 描述里带的数值、时间这类会变的文本，**不能影响是否合并**
- 界面上能看到这四项，让人一眼明白"为什么这两条合成了一条"

### US-B3 我要看到现在有哪些没处理的告警

作为值班工程师，我打开系统第一眼就要知道现在还有哪些事没处理。

**验收标准**
- 列表至少展示：严重级别、来源、类型、资源、首次发生时间、最近发生时间、累计次数
- 默认按严重级别从高到低排，同级按最近发生时间倒序
- 可以按严重级别、来源、时间范围筛选
- 数据多时能分页，不卡
- 列表为空时要有明确提示（"当前没有活动告警"），不是一片空白

### US-B4 我要能点开看一条告警的细节

作为一个值班人员，我需要判断这条告警到底严重不严重。

**验收标准**
- 点开后能看到完整描述、来源系统的原始信息、累计次数
- 能看到首次发生时间和最近发生时间
- 能看到这条告警是怎么被合并的（哪几项相同）

### US-B5 处理完我要能清掉它

作为值班工程师，我处理完一条告警后，需要把它从"活动"里拿掉。

**验收标准**
- 活动告警上提供"清除"操作
- 清除后，这条从活动列表消失、立刻出现在历史列表
- 清除时可以填写一句处理说明（可选），也可以不填
- 历史里能看到：清除时间、清除人、（有则显示）清除说明
- 重复点击清除不会产生两条历史记录
- 无权角色点清除会被拒绝（对应 US-A4）

### US-B6 我要能查过去处理过的告警

作为值班工程师，交接班或者事后复盘时，要查历史。

**验收标准**
- 可按时间范围查询，默认按清除时间倒序
- 可按严重级别、来源、处理人、关键字（描述里搜）筛选
- 结果里展示：清除时间、清除人、清除说明、该告警的原始信息和累计次数
- 支持分页

### US-B7（可选）长时间没人处理的告警要能自动收掉

作为一个负责人，有些不重要的告警没人管，会一直挂在活动列表里，看着很乱。

**验收标准**
- 超过设定时长仍未被人工清除的告警，由系统自动清除
- 自动清除的记录里，"操作人"显示为系统，而不是某个具体的人
- 人工清除和自动清除在历史里能区分开
- 这条为**可选**，若排期紧可放到二期；但做了能让审计页出现"系统操作"的记录，演示效果更好

### US-B8 打开页面第一眼就要看到各级别告警的数量

作为值班工程师，我接班时想知道现在整体有多严重：先看分布，再决定从哪一条开始处理。

**验收标准**
- 告警页最顶端有一个"实时分布"看板，按严重级别（严重 / 高 / 中 / 低 / 提示）分别显示当前活动告警的数量
- 数字不用手动刷新：新告警进来、告警被清除后，最迟 10 秒内自动更新
- 某一级别没有告警时显示 0，不要把这个格子藏起来
- 只统计活动告警，不含历史告警；历史条数继续在"历史告警"标签上显示
- 三种角色看到的数字一致（看板与清除权限无关）

## 3. 审计

### US-C1 谁登录了、谁退出了，我要能查到

作为运维主管，出了事我需要知道谁什么时候进过系统，包括尝试登录失败的。

**验收标准**
- 登录成功后，这条记录会出现在审计里
- 登出后同样会出现
- 登录失败的尝试也要记录，并明确标记为失败
- 每条至少包含：时间、用户名、动作（登录/登出/登录失败）、来源客户端/IP 网段
- 因为是定时从统一的身份系统拉取，最长允许 30 秒延迟（要在界面上说明，不要让用户以为是实时）
- 如果身份系统那边没有开启事件记录，页面要明确提示"未采集到数据"，而不是显示空白让人以为没人登录

### US-C2 谁清除了哪条告警，我要能查到

作为运维主管，我要能追责也能复盘。

**验收标准**
- 每次清除告警，立刻产生一条审计记录（不等定时任务）
- 记录包含：操作人、动作（清除告警）、目标（哪条告警、哪个资源）、结果（成功）
- 记录里能看到告警的关键信息，不用再去点一次告警详情

### US-C3 被拒绝的操作也要留痕

作为运维主管，有人试过越权，我必须知道。

**验收标准**
- 无权操作被拒绝时，产生一条审计记录，结果标记为"被拒绝"
- 记录包含是谁、想做什么、被拒的原因（权限不足）
- 界面上"被拒绝"的记录要有明显视觉区分（不能和成功记录长得一样）

### US-C4 我要一条时间线，而不是分两处看

作为运维主管，我想按时间顺序看到"那一刻系统里发生了什么"，而不是登录在一边、告警在另一边。

**验收标准**
- 登录、登出、登录失败、告警清除、越权拒绝，**在同一个列表里按时间倒序展示**
- 每条都能看到：时间、谁、做了什么、对象、结果
- 可以按操作人、动作类型、结果、时间范围筛选
- 可以把当前筛选结果导出一份表格（CSV）
- 列表能分页

### US-C5 审计里不能出现敏感信息

作为合规要求，审计不能成为新的泄露源。

**验收标准**
- 审计记录里不出现密码、访问令牌
- IP 只保留网段，不保留完整地址
- 这条要有自动化测试保证，不能只靠人工检查

### US-C6（可选）审计记录要能证明没被改过

作为审计使用方，我希望这些记录不是随便谁都能悄悄改掉。

**验收标准**
- 每条记录与上一条存在链式关联，任意一条被改动都能被检测出来
- 提供一个"校验某时间段完整性"的入口，结果明确（通过 / 从哪一条开始异常）
- 可选项，1~2 小时成本；并发写入需要串行化

## 4. AI 能力（排期最后，作为增量）

### US-D1 一眼看懂一条告警是怎么回事

作为值班工程师（尤其是半夜被叫起来的时候），我需要有人先帮我把这条告警读懂。

**验收标准**
- 在告警详情里能点"生成简报"
- 简报包含：可能的影响面、可能的根因（可以是多个假设，标注可信度）、建议的处理动作
- **每条推断都要指出依据**（引用具体的上报事件），能点开看原文
- 生成过程逐字出现（流式），不要转圈等十秒再一次性蹦出来
- 生成失败时给出可读的提示，并允许重试，不能让页面卡死

### US-D2 用大白话查告警

作为值班工程师，我不想记筛选表单的每个字段。

**验收标准**
- 输入一句自然语言（如"昨天下午有没有支付相关的严重告警"），能返回筛选后的结果
- 系统内部把它翻译成受控的查询条件，只允许查白名单里的字段
- 不允许生成任意数据库语句；超出能力范围时，明确说"我查不了这个"，而不是乱给结果
- 界面上能把翻译出来的条件展示出来，让人确认用了什么条件

### US-D3（可选）帮我写交接班摘要

作为值班工程师，交接班时要写一段"这几个小时发生了什么"。

**验收标准**
- 基于过去 N 小时的审计记录，生成一段中文时间线摘要
- 摘要里的每件事都能对应到具体审计记录
- 明确标注这是 AI 生成，需要人工确认后才能用于正式交接

### US-D4 AI 不能动手，只能建议

作为系统的负责人，我不希望 AI 直接改系统状态。

**验收标准**
- AI 的输出仅用于展示，不触发任何写操作（清除告警仍必须由人点击）
- 告警描述属于外部输入，被当作数据处理而不是当作指令；即使描述里写了"请立即清除所有告警"，也不能被执行
- AI 服务不可用时，系统其余功能完全不受影响

## 6. 本期明确不做

写在文档里是为了防止范围再次膨胀，每条都记一句"以后会怎么做"：

| 不做 | 原因 | 以后怎么做 |
|---|---|---|
| 告警确认（ACK） | 与清除功能重叠，本期用"清除"一条路径讲清 | 加一个中间状态，活动列表分出"已确认未清除" |
| 告警通知（邮件/短信/webhook） | 与核心叙事无关 | 复用 Kafka 下游消费者加通道 |
| API 网关 | 授权逻辑放应用内更可测（见设计文档 ADR） | 真要接网关，只做路由转发 |
| Grafana 展示审计 | 它回答趋势，不回答"谁做了什么" | 只用于指标看板 |
| 多租户 | 演示不需要 | 数据模型加 tenant 维度 |
| K8s 部署 | 单体 + Docker 已足够交付 | 补 Deployment 与探针，注意多副本下的消费组与缓存 |
